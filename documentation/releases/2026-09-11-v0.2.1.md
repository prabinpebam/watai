## Production sync incident (2026-09-11)

The original public-shell and health smoke did not establish authenticated data-route
correctness. The S33 queries added two-field `ORDER BY` clauses without deploying the
required Cosmos composite indexes. Both thread and message reads failed with a Cosmos
400 missing-composite-index error, surfaced to the browser as HTTP 500.

Repair changed only the existing indexing policies on `cosmos-watai-cbroocyg3omrk/watai`:

- `threads`: added `/updatedAt` descending, `/id` ascending; policy readback verified
	at `2026-09-11T06:53:49.2302458Z`.
- `messages`: added `/createdAt` ascending, `/id` ascending; policy readback verified
	at `2026-09-11T06:54:28.3244836Z`.
- Both original query shapes reproduced the failure before repair and returned a row
	afterward. Production request telemetry subsequently recorded two `threads` HTTP 200
	responses (latest `2026-09-11T06:55:06.8137945Z`) and three `messages` HTTP 200 responses
	(latest `2026-09-11T06:55:07.3895093Z`).
- All other indexing properties and partition keys were preserved and compared against
	readback. No documents, app settings, roles, runtime, frontend, or API package changed.

Main and stage Bicep templates now declare these indexes. Existing Cosmos integration
test files assert the index definitions explicitly. Templates compile and API typecheck
passes; the new integration assertions were not run against production because the
integration runner correctly prohibits production targets. The verification browser was
signed out, so UI interaction was not independently tested; actual production HTTP 200
requests supply the affected-route recovery evidence.

Original policies and readback snapshots are retained under `.harness-state/incident-*`.
Keep the additive indexes during code rollback; removing them would reintroduce the
outage for the serving query contract. Do not deploy the full infrastructure template
as an incident rollback or restore older user data.
